# Contributing to docxtpl-lint

Thanks for your interest in improving docxtpl-lint. This document covers the
practical steps for setting up, testing, and submitting changes.

## Development setup

```bash
python -m venv .venv
. .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -e ".[dev]"
```

## Checks before submitting

Run the test suite:

```bash
pytest
```

Run linting and formatting checks:

```bash
ruff check . && ruff format --check .
```

Both must pass. Please keep changes focused; unrelated refactors make review
harder.

## Project layout

- `src/docxtpl_lint/messages.py` — rule definitions: `id`, `severity`,
  `summary`, and the `en`/`zh` messages.
- `src/docxtpl_lint/core.py` — rule implementations.

## Adding a rule

Rules must be deterministic. Prefer missing a report over emitting a false
positive. Automatic fixes are out of scope — do not add them.

When adding a docxtpl-related rule:

1. Define the rule in `src/docxtpl_lint/messages.py` and implement it in
   `src/docxtpl_lint/core.py`.
2. Add a **bad** case to `tests/rule_cases.py`, and a **good** case whenever
   one is meaningful.
3. `tests/test_docxtpl_behaviour.py` renders the cases with the real `docxtpl`
   package to prove the problem actually exists (either it `raises`, or it
   fails `silent`). Make sure your case is covered there.

## Fixtures and demo assets

- Example `.docx` files are generated by `tests/make_fixtures.py`.
- README screenshots are generated by `scripts/make_demo.py` (requires
  `rich`).

Regenerate these when your change affects them, and commit the results.

## Reporting bugs

Open an issue with a minimal `.docx` that reproduces the problem and the
`docxtpl` version you are using. Without a reproduction we usually cannot
confirm the behaviour.

## Commits and changelog

- Write commit messages in the imperative mood (e.g. "Add rule for ...").
- Add an entry to the `Unreleased` section of `CHANGELOG.md`.

## Pull requests

Keep each PR scoped to one change. Describe what the rule or fix does, and
reference the issue it addresses. Ensure `pytest` and `ruff` pass locally
before requesting review.
